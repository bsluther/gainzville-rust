## 2. Architecture frame: Spec → Type → Value

Three levels, the backbone of everything below:

- **Spec** (persisted, synced): catalog-free — IDs and structure only, no derived facts.
  Rationale (recorded in draft.rs header): if derived info were stored, "re-run on what?"
  — you'd have to disentangle the catalog-independent part anyway; that part *is* the spec.
- **Type** (derived, never stored): `resolve(spec, catalog) → typed schema` — one pass
  that is simultaneously validation (staleness gate: names the broken leaf), schema
  derivation, and the builder's legal-options oracle. Runs at build, load, catalog change.
  **Schema-determinism**: types are a pure function of spec + catalog, never of data.
- **Value** (execution): the in-memory interpreter over loaded domain data. Cells are
  bare; the type sits on the column, once; cell ↔ column pair by position.

The type/metadata split follows an **observability criterion**: machine-observable &
catalog-derivable facts are *type* (incl. domains, unit dimension, ordered-ness);
display residue (labels, descriptions, default display unit) rides alongside;
data-dependent facts (observed extents, distinct text values) are *instance*, never schema.

## 3. Query-side leanings

### 3.1 Pipeline shape (see draft.rs, Spec section)

```
PipelineSpec  { source: BaseSource, segments: Vec<Segment> }
BaseSource    = Entries(EntriesSource)            // enum of per-kind structs (2026-07-11)
EntriesSource { id: SlotId }                      // one Entry slot = the Entry collapse
Segment       { filters: Vec<Expr>, group_by: Vec<OutputDef>,
                aggregates: Vec<AggregateDef>, having: Vec<Expr> }  // having 2026-07-10
OutputDef     { id: SlotId, label: Option<String>, expr: Expr }
```

- **Explicit base source** minting slots (reversal of the earlier "implicit BaseSource"
  — which survives only as a UX statement: the builder shows no FROM clause). Source
  constructors are their own species (`BaseSource`), deliberately *not* `Expr`
  variants — a nullary generator is a different species from a map over rows, and putting
  it in the expression grammar would make it representable everywhere and legal nowhere.
  This is also the extension seam: saved-spec-as-source and (if ever) joins arrive as new
  source declarations minting slots. **Slots live in the variant (decided 2026-07-11)**:
  `BaseSource` is an enum of per-kind structs (the codebase's structs-plus-grouping-enum
  pattern) — `Entries(EntriesSource { id })` — because a source's schema is a slot *set*
  and the arity is kind-specific: `Entries` mints exactly one Entry-typed slot *because
  of* the Entry collapse (§3.2), while a saved-spec source introduces its child's whole
  output schema. The earlier decl-level single `id` (`BaseSourceDecl { id, kind }`)
  baked singleton arity into every future kind, neutering the very extension seam the
  enum exists for; the wrapper dissolved with the move (declaration-ness is positional —
  the spec's `source` field), and `Kind` dropped from the enum name since it now carries
  data. Open sub-question when saved-spec-as-source lands: fresh-mint + mapping (keeps
  specs self-contained) vs re-exposing the child's ids — touches the
  catalog-names/inlining question.
- **Definition site vs use site**: `OutputDef` *creates* a slot; `SlotRef(id)` *mentions*
  one. A reduce is a binder. Minting sites: the `BaseSource` variant structs
  (`EntriesSource`), `OutputDef`, `AggregateDef` (plus its `AggregateBinding`s' local
  slots), and the forest-op binder (§3.3).
  Expressions may reference only the
  **immediate input schema** (previous segment's outputs; the base slot for segment 1);
  a reduce consumes its input — carry things forward by re-emitting them. With binders,
  "input schema" generalizes to the current **scope** (§3.3); for segment-level
  expressions the two coincide.
- **Substitutability distinction** (why slots aren't "addresses of expressions"):
  *definitional* references (catalog names, same-grain derived values) can be inlined
  away; *stage-output* references cannot — `filter climbs ≥ 10` cannot inline `count()`
  because that expression belongs to the previous segment's grain. Downstream, a slot is
  data; its defining expression is provenance (explains the type; never re-evaluated).
- **`SlotId`**: opaque `Uuid` newtype, minted at authoring, carrying nothing. The same
  ids are the "stable output-column ids" ChartSpec bindings use — one identity scheme,
  two consumers; renames dangle nothing.
- **Grain legality = scoping, with zero special rules.** An expression is legal iff every
  slot it references is in the current input schema. Entry-grain-only operations are
  entry-grain-only *because* their operand bottoms out in the Entry slot, which stops
  being in scope after a non-entry-keyed reduce.
- **`having` (decided 2026-07-10).** Post-aggregation filters are a fourth clause on the
  segment, `having: Vec<Expr>`, resolved against the segment's **output** schema (its
  group_by and AggregateDef output slots) — the same environment that becomes the next
  segment's input, so
  resolve is the existing machinery with a different env argument. This replaces the
  earlier "post-agg filters are just segment-2 filters" claim, which was unsound: a
  filter-only segment has an undefined output schema, and every re-emission workaround
  either has no semantics (bare `SlotRef` in aggregate position) or changes them (measures
  re-emitted as group keys) — and all of them mint fresh SlotIds, orphaning ChartSpec
  bindings on the common edit "add a HAVING to an existing chart". Malloy-verified
  (2026-07-10 source read, `~/dev/clones/malloy`): Malloy's `having:` lives in the same
  reduce segment resolved against the output field space (filters.ts:194–205; one shared
  filterList partitioned by expression type at SQL-gen), and filter-only stages are
  explicitly forbidden as ambiguous (`'partial'` segments error `ambiguous-view-type`,
  query-utils.ts:10–30). For GV, position discriminates (a separate `having` field), not
  expression-type inspection — consistent with group_by vs aggregates. Cost accepted:
  two filter lists with different scopes on one struct; structure doesn't show it, so it
  must be documented. `having` references sibling outputs but never defines — no
  acyclicity concern.
- **Projection** (per-row derived columns without aggregation — the per-entry scatter
  case) is deliberately a **separate, later mechanism** — not solved by `having`, and not
  by pass-through/filter-only segments (rejected; see above). Default candidate: a
  project segment kind as a peer of reduce — Malloy's shape, though Malloy encodes it as
  the identical struct with a different tag (legality by validation); GV would likely use
  the codebase's structs-plus-grouping-enum pattern (legality by construction).
  Alternative on file: a `derives: Vec<OutputDef>` clause on the one struct
  (dplyr-mutate-style; buys within-segment expression reuse, reopens
  degenerate-clause-combination questions). Undecided.
- **Aggregate layer (decided 2026-07-10; representation revised same day): two phases,
  folds as let-bindings.** The stratification *principle* stands: every expression is
  per-row or per-group, decided by **position**, never by inspection (the
  unified-grammar + resolve-time-checks alternative stays rejected — Malloy needs
  inference because its users type text; a machine-authored spec gets position for
  free). The first-cut *representation* — a mirrored `AggExpr` enum
  (Agg/Unary/Binary/Literal/Transform) — was replaced when its curated variant list
  showed an accretion problem: it was already missing `EntryAccessor` over Entry-typed
  keys (§3.2's own regime rule), and every future `Expr` addition would need
  re-adjudication at the mirror level, forever. Revised shape:

  ```
  Segment          { filters, group_by: Vec<OutputDef>, aggregates: Vec<AggregateDef>, having }
  AggregateDef     { aggs: Vec<AggregateBinding>, id: SlotId, label: Option<String>, expr: Expr }
  AggregateBinding { slot_id: SlotId, aggregation: Aggregation }   // local slot per fold
  Aggregation      { function: AggFunction, operand: Option<Expr>, filter: Option<Expr> }
  ```

  Fold operands and per-aggregate filters are per-row **input-scoped** `Expr`s with full
  power (`sum(weight × reps)` = an operand expression; accessor chains, transforms,
  forest ops all legal). The combining `expr` is **plain `Expr`** resolved against the
  *combining scope* = agg-binding slots ∪ group_by key slots. There is no mirrored
  grammar: "what's legal above the fold" is **derived by scoping**, not curated — a
  per-row SlotRef is out of scope; `EntryAccessor` type-checks only against an
  Entry-typed key slot; `day(max(instant))` ("date of last session") is an ordinary
  Transform over an agg slot. Nested aggregation stays unspellable: `Aggregation` is
  not an `Expr` variant, and operands resolve against the input env, which contains no
  agg slots. The per-aggregate `filter` (Substrait measures / Malloy `aggregate:
  {where:}`) — not sibling refs — is what differently-filtered counts (send-rate)
  actually need.
- **Placement rule** (settled `Aggregation`'s home; generalizes to any boundary node):
  a node lives at the level **where its result lives, not where its operands come
  from**. `Aggregation` consumes per-row values but *is* a per-group value — evaluating
  it against a single row's env is meaningless — so it can never be an `Expr` variant
  (that would also readmit aggregates into filters and make `sum(sum(x))` spellable).
  The dual case confirms the rule: `NearestAncestorWhere` rebinds its *child's* scope
  but itself evaluates per-row, so it stays in `Expr`.
- **What the revision resolves.** Sibling references: fully — a shared fold is two refs
  to one `AggregateBinding` (the original DRY motivation); group-key math (`count /
  week_number`) works because key slots are in the combining scope. `Count.operand` is
  `Option`: None = count rows, Some(e) = count *present* values (SQL's
  `count(*)`/`count(expr)`; dovetails with absence semantics). Degenerate segment
  shapes all defined: empty group_by + aggregates ⇒ one grand-total row (whole input =
  one group); group_by + no aggregates ⇒ distinct; both empty ⇒ illegal (a segment must
  mint outputs; `having` covers post-agg filtering). Eval needs no second expression
  walker: per group, compute folds into an env, then plain `eval_expr`. `AggregateBinding`
  slots are **local** — excluded from the output schema and never chart-bound (one
  rule). Still owed: the aggregate typing table (Count→Int; Sum/Min/Max gated by
  scale; Avg's dimension behavior) — feeds the Type-section rebuild.
- **Prior-art check (2026-07-10; two research agents: Malloy source read + general
  survey).** Verdict: decomposed-at-rest is the **canonical choice for a machine-authored
  persisted spec**. The split is clean and correlates with authorship: inline-tree-with-
  inspection is exclusively human-typed surfaces (SQL, Malloy, dplyr, Tableau/DAX,
  Polars/Ibis) — and every one of them decomposes into folds + a scalar layer before
  execution anyway (Postgres: `Aggref` → per-agg `aggno` slots read by the projection at
  the executor; Spark: `PhysicalAggregation` splits `aggregateExpressions` from
  `resultExpressions`; DataFusion/DuckDB: Projection-over-Aggregate at logical
  planning). Decomposed-at-the-surface is exactly the machine-authored cohort: Substrait
  (`AggregateRel` + `ProjectRel` — inline unrepresentable by grammar, AggregateDef's move),
  Druid native (`aggregations` + `postAggregations` — nearest single precedent), MongoDB
  (`$group` accumulator-rooted + `$project`), Vega-Lite (`aggregate` + `calculate`),
  Elasticsearch (`bucket_script`), LookML (`type: number` measures over `${name}` refs).
  Per-aggregate filters are ubiquitous (SQL `FILTER`, Substrait measure filter, Druid
  filtered aggregator, Spark/DataFusion filter fields, LookML `filters`). Malloy
  specifics (source-verified): fully inline camp — `AggregateExpr` is an ordinary `Expr`
  node, aggregate-ness inferred bottom-up (`maxOfExpressionTypes` lattice),
  aggregate-of-aggregate representable-but-rejected, inline tree survives to SQL text;
  its filtered aggregate is a `FilteredExpr` wrapper *outside* the aggregate (opposite
  nesting from `Aggregation.filter`, same semantics). **One uncommon detail in AggregateDef:
  per-output-local binding scope.** Surveyed systems bind folds at stage level in two
  shapes: engines as an *internal* pool (Postgres `aggno` slots, Spark deduped
  `aggregateExpressions` — enables fold dedup), pipeline formats as *public output
  columns* (Druid/Mongo/Vega-Lite — combining is a separate downstream stage;
  intermediates pollute the output schema). Neither cohort persists-and-edits query
  ASTs: engines regenerate plans from text per query; pipeline specs are emitted
  wholesale by client code. Shared bindings are only hazardous under structural
  editing — exactly GV's model — and the one surveyed system with per-definition
  editing of persisted formulas (DAX measures) is the one that chose per-output
  locality (`VAR … RETURN`). Cost accepted: an identical fold used by two outputs
  folds twice without CSE — negligible for the in-memory interpreter; leave a comment
  when implementing. Datum for the queued catalog-names
  question: Malloy's persisted queries keep named-measure references **by name**
  (`RefToField`), inlining only at SQL generation.
- **Reduce-segment phase/scope map** (the shared mental model):

  ```
  input rows                      scope: input slots (prev segment's outputs / base slot)
    │ filters                     — per-row, input scope
    │ group-key exprs             — per-row, input scope (group_by OutputDefs' exprs)
    ▼ partition by key tuple      [StringSet keys fan out — §3.4]
  groups
    │ fold operands + per-agg filters — per-row within each group, input scope
    │ folds (Count/Sum/…)             — per-group
    │ combining exprs                 — per-group, combining scope (agg ∪ key slots)
    ▼
  output rows                     scope: key slots + AggregateDef output slots
    │ having                      — per-row over output rows, output scope
    │ [order_by / limit — future, output scope]
    ▼ next segment's input scope = this output scope
  ```

  A group_by key slot has a **dual nature** — one value, two grains: its expr evaluates
  per-row (assigning membership), and the same value is *promoted* to per-group standing
  (the group's identity), licensed by constancy-within-group. That promotion is what
  lets Entry-typed keys carry the entry vocabulary across a reduce, and what makes key
  slots legal in the combining scope. **Scope inventory (complete)**: input, binder
  (forest-op predicates, fresh `{binds}`), combining, output — all four the same
  env-passed-down machinery, differing only in which slots go in.
- **Grammar taxonomy (2026-07-10).** Grouping criterion = shared resolve/eval machinery
  + scope contract — explicitly NOT "consults ambient context", which overgeneralizes
  (accessors read values/forest too). Four species: **operators** (payload-free,
  typing-table-driven, same-scope children: Unary/Binary), **transforms** (payload
  participates in typing, single same-scope operand: `TimeTruncation` — evicted from
  `UnaryOp` — with `bin`/`band` to follow), **accessors** (catalog-typed reads off an
  Entry operand), **scope-rebinders** (binder-minting, rebound child scope:
  `NearestAncestorWhere`). TimeTruncation's eviction rationale: payload flows into the
  result type if Q4 lands `TimeBucket{grain}`; consults per-spec tz/week-start; family
  cohesion with non-unary bin/band. Transforms at the agg level are real —
  `day(max(instant))` = "date of last session".

### 3.2 The Entry collapse (the biggest structural lean)

At the base source, the schema is **one slot of type Entry**. Every entry-grain "column"
— instant, activity, weight, grade — is an **accessor expression** over that slot
(`EntryAccessor`: Instant/Start/End/Duration/IsSequence/IsComplete/Activity/Attribute).
This is Malloy's own architecture (a source's dimensions are expressions over the row),
re-derived from the type-system side; the "wide pivot" of earlier docs was only ever a
SQL-lowering strategy, which the in-memory interpreter never needed.

- **Attributes are not a type** — an attribute is a *family of columns*, and
  `Attribute { attr_id, aspect: Option<Aspect>, range_fold: Option<RangeFold> }` is a
  **qualified name** (which member of the family), not a runtime operator. `Option` =
  "use the default" (Actual, Mean) so saved specs don't bake defaults in. There is no
  `plan(x)` operator anywhere — that expression is unrepresentable, which is what lets
  the checker stay scalar-only. (If a *textual* expression language ever exists, this
  needs revisiting: parsing `plan(weight)` as application would force attribute-typed
  intermediates.)
- **Accessor operands are explicit** (`EntryAccessorExpr { accessor, operand }`), never
  implicit-self. Three payoffs: legality-by-scoping; chaining (accessors on ancestor
  results); and the re-grain case (accessors on Entry-typed *key columns* at coarser
  grains). The builder may still *display* bare "weight" — sugar lives in the UI, one
  spelling in the spec.
- **Two regimes**: entity regime (entry grain — one Entry slot + a library of named
  expressions) and data regime (post-reduce — genuine data columns). Entry-ness survives
  a reduce **only through Entry-typed keys**: grouping by e.g. the session identity
  yields rows still indexed by entries, so the whole entry vocabulary re-applies via the
  key (the session's instant, its attributes). Grouping by a time bucket or attribute
  value kills it. This gives the old "entry-shaped vs result-shaped" intuition a precise
  mechanism.

### 3.3 Forest operations

- **Binder decision (2026-07-10).** `NearestAncestorWhere { operand, binds: SlotId,
  predicate } : Entry → Entry` is its own ExprSpec variant, not a `BinaryOp` (binary
  operators keep the evaluate-both-children-in-the-same-scope contract). The predicate
  runs against a different row-stream — each candidate ancestor — and previously nothing
  could *name* a value in that context: the flagship predicate `activity ==
  ClimbingSession` was unwritable (found independently by both reviewers in the 07-10
  review round). Fix: the node is a **binder** — it mints `binds`, the slot naming the
  candidate ancestor; the predicate references it via ordinary `SlotRef(binds)` and
  accessors chain off it exactly as off the base slot. Note `binds` is the analogue of
  the *source's* id (names the rows coming in; the operator writes each candidate into
  it, the predicate reads), not of an `OutputDef`'s id (names a computed result).
  Unifying frame that sold it: the operator is a tiny nested pipeline — source = the
  ancestor chain, filter = predicate, take nearest — and `binds` is that mini-source's
  slot declaration, the same declaration-mints-a-slot move `BaseSourceDecl` makes.
- **Scope becomes a stack** (flat-per-segment → lexical), implemented as an environment
  parameter threaded through the resolve/interpret recursion: definitions flow *down*,
  `SlotRef` is an env lookup — never search the tree for a definition site. v1 scope
  rule (no references from the predicate to the outer row, i.e. no correlation) =
  resolve the predicate against a *fresh* env `{binds: Entry}`; enabling correlation
  later = extend the outer env instead, a one-line change. The hard parts of lexical
  scoping are absent here: no escaping closures (a predicate never outlives its node's
  evaluation), no shadowing (UUID slot ids can't collide by name), one-pass top-down
  resolution. New obligations: a mint-uniqueness walk over the spec (collect all minted
  ids, error on duplicates), and — for error quality — distinguishing "unknown slot"
  from "exists but out of scope".
- **`HasAncestorWhere` dropped as a variant** — compose as some/is_some over
  `NearestAncestorWhere` instead. Its exact shape hangs on the absence/null-semantics
  question (§5).
- **Alternatives considered and passed on** (recorded so they aren't re-litigated): an
  implicit-self leaf (`ExprSpec::Candidate`) — cheaper, but representable everywhere and
  legal in exactly one place (the disease the source-exclusion argument names), and its
  fixed innermost-binder meaning makes the outer candidate unnameable under nesting; a
  closed `EntryPredicate` DSL (defunctionalized condition rows, cf. README's old
  predicate-depth-cap lean, whose FFI motivation the crosses-as-JSON decision mooted) —
  enforces no-correlation *by construction* and mirrors the condition-row UI, but is a
  second expression grammar to keep in sync, and correlation stops being additive. The
  DSL shape may still serve as the *builder's* authoring model compiling to the spec
  form (sugar in the UI, one spelling in the spec). Prior-art line that framed the
  choice: machine-manipulated JSON IRs use named binders (MongoDB `$filter`/`$map`:
  `as:`/`$$x`); implicit-self belongs to human-typed languages (NSPredicate `SELF`,
  jq `.`).
- "Session" is not a primitive: *group by session* = group by
  `NearestAncestorWhere(P_session, ⟨entry⟩)`, an Entry-typed key.
- **Ambient-context principle**: operator evaluation may consult read-only context fixed
  for the run — the Forest (ancestor walks), the category closure later (`in_category`).
  Deterministic; precedent: a join is exactly this. This is also why Position died as a
  type: a bare parent id can't answer transitive questions; the *operators* consult the
  forest, and nothing ever evaluates *to* a position.

### 3.4 Type system (draft.rs Type section — older; queued questions live here)

- **`DataTy` is the primary axis** (operator dispatch): Boolean, Int, Float, String,
  Timestamp, Length, Duration, Mass, StringSet, Entry, Activity.
- **The earning rule**: a type exists iff some expression can evaluate to it (literal,
  slot value, or operator/accessor result). Activity stays (accessor result + literals
  for `activity == X`); Position died (nothing evaluates to one); Category joins when
  the DAG lands (`in_category` needs Category literals).
- **Scale (Stevens: Nominal/Ordinal/Interval/Ratio) is type information but *derived*** —
  a function of type + config (a Select is ordinal iff its config says ordered), not a
  stored second field. It gates operator/aggregation legality (`<=` on ordinal strings
  only; `avg` never on ordinals) and feeds the chart's per-column measurement class.
  Timestamp is Interval (affine: ts−ts→Duration, ts+ts illegal); **Duration is Ratio**
  (summable — weekly volume), as are Mass/Length/Int/Float.
- **Dimension is type; unit is presentation.** Mass/Length/Duration as flat variants
  (`weight + distance` must not type-check); cells are SI-normalized; display unit is a
  ChartSpec choice, converted at render_model. Encoding note: flat variants vs
  `Number{dim}` is isomorphic; flat chosen, repetition accepted.
- **Domain is part of the type** (a Select's options are its identity: cross-Select
  comparison illegal, literals validated for membership, `max` carries the label,
  group-by output inherits the full domain → empty chart buckets). Closed domains come
  from the catalog; open "domains" (Text values, numeric extents) are data → instance
  facts, never schema. `IntTy { min, max }` bounds are legal only if config-declared.
- **Identity types** (Entry, Activity): cells are `Uuid`s; `==`/`in` compare identities;
  display resolves through the catalog (store-IDs rule). `in_category` should persist
  intent (`category_id`) and expand at resolve.
- **Fan-out** (StringSet group keys, future categories): grouping by a set-typed column
  duplicates the row per member; empty set → no group; the output key column re-types
  `StrSet{domain} → Str{domain}`; totals exceeding the grand total is the *named* policy
  (unweighted "impact"; 1/n allocation is the deferred alternative); the output schema
  should carry a **non-partitioning** flag (feeds pie legality, honest percent-of-total).
- **Additivity** (additive vs point measures) looks like a derived property of the
  producing expression — feeds zero-baseline and pie rules; not designed.

### 3.5 Code conventions

Individual structs + thin grouping enums (the codebase's Action/Query pattern; behavior
as methods on nameable leaf structs, enums as membership/dispatch). Tuple variants only
for single-scalar leaves (`Literal`, `SlotRef`). Serde will be external-tagged (workspace
`arbitrary_precision` constraint); spec needs a version field from day one; recursive
`ExprSpec` is fine core-side — the spec crosses FFI as JSON (AttributeConfig precedent),
with the builder producing bounded shapes.

Naming (2026-07-10): the `Spec` suffix marks **persisted artifact roots** only
(`PipelineSpec`, `ChartSpec`); interior grammar nodes go bare — draft.rs renamed
`ExprSpec → Expr`, `SegmentSpec → Segment` (serde-free: external tagging writes variant
names, never type names). Correspondence per expression: `Expr` (authored) : `Ty`
(derived) : `Cell` (executed). Payload structs take an `Expr` suffix only to
disambiguate from a separate operator-vocabulary type (`UnaryExpr` vs `UnaryOp`,
`EntryAccessorExpr` vs `EntryAccessor`); where operator and application node coincide,
the bare name stands (`NearestAncestorWhere` — matching bare Action leaf structs).
`Any*` is reserved for erasure wrappers over standalone families (`AnyTy`, `AnyDelta`),
never for composition grammars — rustc/syn precedent (`Expr`, never `AnyExpr`).
**Two-tier vocabulary rule**: scalar/aggregate name the *expression tier* (Malloy's
`expressionType` values and its `aggregate:` query clause; GV's `aggregates:` field and
the `Aggregation`/`AggregateDef`/`AggregateBinding` types), while dimension/measure/metric are
*catalog-tier* words reserved for named fields (Malloy declares `measure:` on sources;
POC note: "queries just say `aggregate: tonnage`") — keeps the namespace clean for
stdlib/named metrics; the rule already caught one `MeasureDef` slip in a working
sketch. **Field name = phase, struct name = shape**: Segment fields carry the phase and
therefore the scope (`filters`/`group_by` → input, `aggregates` → combining, `having` →
output); struct names carry shape — `OutputDef { id, label, expr }` is the generic
slot-minting record (group_by today, Project outputs later), `AggregateDef` the
aggregates-position record. Names never encode phase; position does.

## 5. Open questions — the queue

Numbering continues the working session's review list where it existed.

**Q3 — RESOLVED 2026-07-11: `LiteralSpec`.** Derivation rule: **a literal form exists
iff some builder interaction produces one**, stored *as-entered* where round-trip
matters. The variant list:

```
LiteralSpec = Bool(bool) | Int(i64) | Float(f64)
            | String(String)                  // free text AND Select labels; membership checked at resolve
            | Mass   { value: f64, unit }     // as-entered; SI at the cell boundary
            | Length { value: f64, unit }     // as-entered
            | DurationMs(u64)                 // canonical; builder formats (weakest lean)
            | Date(chrono::NaiveDate)         // civil y/m/d, no tz — instant via per-spec tz at eval
            | RelativeTime { anchor: Now | StartOf(TimeUnit), offset: (i64, TimeUnit) }
            | Activity(Uuid)                  // catalog identity; resolve validates existence
            | List(Vec<LiteralSpec>)          // In's RHS; homogeneity checked at resolve
```

Decisions inside: `Int`+`Float` as two variants (the builder knows the compared field's
type, so precision is free). Duration canonical-ms (durations format canonically; they
don't unit-preserve the way Mass does). `RelativeTime` (renamed from RelativeDate
2026-07-11 — it evaluates to an *instant*, not a date) is the **packaged** form
(defunctionalized — fine here because the composition space is tiny, unlike the rejected
`EntryPredicate`), evaluates to a **Timestamp** boundary; `Today` collapsed into
`StartOf(Day)`; `Now` vs `StartOf` = rolling/ragged vs bucket-aligned windows
(`StartOf(Week)` consumes the per-spec week-start). Sub-day offsets ("4 hours ago") are
*not yet expressible* — `TimeUnit` has no `Hour`; deferred until earned, and adding it
means deciding (a) shared `TimeUnit` (truncate-by-hour becomes representable) vs a
separate offset-unit enum, and (b) writing down the offset-arithmetic rule (calendar-
aware per unit, in the ambient tz — months/years are variable-length; days cross DST;
hours are the first absolute unit). **All time literals evaluate at execution against
ambient (tz + Clock-injected now)** — `Date` could constant-fold at resolve but stays
uniform with `RelativeTime`. `Date`'s payload is `chrono::NaiveDate` (clean ISO-8601
serde, unlike chrono `Duration`); the *variant* is named `Date` — external tagging
persists variant names, so wire tags use spec vocabulary, not chrono jargon. Open input
for the Type rebuild: where `Date` fits (`DataTy::Date` inhabited only by literals, vs
a comparison-table rule accepting (Timestamp, Date) pairs with contextual half-open
expansion). **Date-in-comparison boundary rule**: a
date expands to the half-open day interval `[start(d), start(d+1))` — `>= d` uses the
lower bound, `<= d` means `< start(d+1)`, and the builder's BETWEEN desugars accordingly
(kills the excludes-the-last-day off-by-one). Excluded by the earning rule: `Entry`
(data-identity — sync-unsafe, no builder intent picks a specific entry), `StringSet`,
`TimeBucket`, `DateTime`-with-time, and `CivilTime`/day-of-week — the latter two arrive
*paired with their transforms* (TimeOfDay / DayOfWeek) like TimeTruncation+TimeBucket;
recorded as future pairs. Riders now unblocked: `Expr::Literal(LiteralSpec)`; **`Cell`
drops to SI scalars** (Mass/Length → bare `f64` SI, Duration → integer ms; chrono only
for `Timestamp` — kills the chrono-Duration serde landmine); `In :: (T, List<T>)`;
`version` field on `PipelineSpec`.

*Original problem statement (kept as rationale):* embedding runtime `Cell` in persisted
specs (a) couples the serde format to execution types; (b) can't serve both as-entered
literals and SI-normalized cells; (c) gives `In`'s set literals no home; (d) leaks
runtime-only chrono types into the persisted format. Three-layer unit story: literal
as-entered → cell SI-base → display re-united at the chart edge.

**Q4 — what does `TimeTruncation` return?** Candidate: `TimeBucket { grain }` as its own
type (a period: value = start instant + grain) — charts need the grain per column, the
spine attaches to buckets, and bucket arithmetic differs from Timestamp's. Also here:
timezone + week-start live **per-spec** (one field on the root, not per-op), per the
earlier determinism decision.

**Q5 — Domain/Order collapse + the missing payloads.** `Order::Discrete(Vec<C>)`
duplicates `Domain::Discrete(Vec<C>)` — two vecs that can drift; lean: `Closed { values,
ordered: bool }` (rank = domain order, the settled Select rule). String/StringSet still
lack their domain payloads in draft.rs — the load-bearing part of the whole domain story.

**Q6 — trait `Ty` vs enum-with-methods; where `Carrier` lives.** The trait isn't
object-safe with an associated `Carrier` (the sketched `Box<dyn Ty>` won't fly), and
cross-method consistency (kind=Int ⇒ order=Natural) is unenforced. Recorded lean:
`AnyTy` as the single source of truth with methods (`scale()`, `domain()`, …) whose match
arms are consistent by construction; `DataTy` derived by a method; the (AnyTy, Cell)
correspondence is the interpreter's match, not a type-level association. The genuine
counter-question (user's): how to express `Domain<C>`/typed payloads without a generic
carrier — what does the fully-enumerated version look like concretely?

**Q9 — Spec vs Def naming.** Exploratory; "Spec" currently used everywhere
(PipelineSpec/ExprSpec + ChartSpec docs); rename only if clearly better.

**Q10 — `IntTy { min, max }` provenance.** Keep, but bounds must be **config-declared
only** (RPE 0–10), never data-observed — schema-determinism. Needs a comment/enforcement
home when the Type section gets rebuilt.
